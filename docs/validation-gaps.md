# Validation gaps — what has *not* been verified

This page separates what the Mac port has been shown to do (see `validation-history.md`, `validation-full-port.md`, `validation-bak.md`, `history-report.md`, `kml-export.md`) from what has **not** been verified. Nothing on this page may be read as "works"; each row names the missing evidence. A row leaves this page only when the evidence exists and is linked from the validation documents.

**CI status:** the 16分割表示 change (commit `7d0e57d0`) was first built and tested in run #132 (commit `b600745f`) after the owner re-enabled GitHub Actions: unit tests, the signed app build, the extracted-package check, the GUI self-check (including the 16分割 menu and sheet check on the generated test pattern) and packaging all passed (387 tests). Run #133 (documentation commit `c8c945fc`) repeated the same checks and published the pre-release `v0.2.0-beta.2`. Before that, run #130 and a manual diagnostic workflow (`ubuntu-latest`, `macos-15`, `macos-14`, `macos-latest`) had failed within two seconds with no runner assigned (an availability problem of the account, not of the code), and run #131 failed to compile because of one Swift lexical error (`projection.mode=.perspective`, fixed in `b600745f`).

Earlier verified CI: run #126, 378 tests, 0 failures, signed app, extracted-package check, GUI check and settings smoke (including delete / initialise on copies) passed. Build 13 (run #82) and the build-14 artifact of run #128 were run on a real Mac with real data (build 14: lists, history report CSVs, KML, BAK writer and delete/initialise on clones of the sample card image; `validation-full-port.md`). The exact release assets of build 15 (`v0.2.0-beta.2`, with the 16分割 screen) were later verified on a Mac with the sample card's image (`validation-full-port.md`, section "Build 15"): lists, history report CSVs, KML, the MP4/AVI/PNG/print/report-PDF exports of a real event recording, the BAK writer, delete/initialise on clones and the destination-full behaviour of the MP4/AVI/BAK exports. The packaged GUI check ran on the real event recording up to a harness step that wrongly assumed a continuous recording. That pass also showed that the sample card's 18 continuous recordings carry **no video** (zero-filled video areas), which build 15 reported as an obscure SPS/PPS alert; build 16 (the next pre-release) shows a neutral notice instead. Still **not** run on a Mac: build 16, AVI beyond 4 GiB with real video (the card has about 1,800 real frames per event only), playback/export of real continuous video (none exists in the image), and the physical SD path. Everything else the newest builds added is verified by CI (synthetic data, differential tests against independent reference scripts) and by comparisons made on the Linux machine that runs the original application.

## Settings, password and format operations

Tracked in `settings-format.md`, `recording-data-operations.md` and `destructive-operations.md`. In short: every setting field the Mac port writes was derived from the original's own writes on a scratch copy and is limited to the Q-01 class. The password (set, change, clear, ask on open), 録画データ削除 and 記録設定データ初期化 are implemented for that class on **new image copies only**; the reader rule behind 削除 is verified at card generation 1 only (see above). The settings of the other five dialog classes, week-timetable, person-detection and Wi-Fi settings, the model-specific initialisation (format flow), quick/full format and firmware update are analysed in part or guarded but never executed against an original medium. The original's format flow was observed only up to the partition table, the FAT16 boot sector and the first FAT sector (a Wine stub then stopped it).
