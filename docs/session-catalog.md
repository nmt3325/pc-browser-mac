# 連続録画と高速索引（v0.2.0-beta.2）

## なぜ450フレームで分かれていたか

今回のカードでは30fps × 約15秒 = 450フレームの内部保存ブロックが繰り返される。旧Mac版は`recordSector + channel`をそのまま一覧の1件としていたため、保存ブロックの境界がユーザーの録画境界になっていた。450枚ごとに実際の録画開始・停止を検知していたわけではない。

### 実IMGで照合した参照

|領域|オフセット|意味・検査|
|---|---:|---|
|D103/D105|0x004 / 0x1FC|保存ブロック識別子と複製値|
|D103/D105|0x098|連続録画内の累積フレーム位置|
|D103/D105|0x09C|連続録画のシリアル|
|D103/D105|0x1C4|録画開始D103へのLBA参照|
|D103/D105|0x1E0|管理ヘッダー自身のLBA|
|D103/D105|0x1F8|循環記録の世代。録画開始IDとしては使わない|
|D101|0x1B8 / 0x1DC / 0x1D8|管理LBA・ブロック識別子・循環世代。対応する管理ヘッダーと一致すること|
|D101|0x1C0|直前パケットへのLBA参照。保存ブロックをまたぐ|

常時記録では開始D103の参照は自身を指し、累積位置は0である。**特別記録領域のD103には、既存の開始LBAを参照し累積位置が0でないものもある**。D103という署名だけで別の起動と判定しない。D105は継続ブロックとして同じ開始参照を持つ。2つの隣接する管理セクターは全バイト同一ではないため、映像D101/D102と同じ「複製完全一致」検査を適用してはいけない。

新Mac版は**開始LBA・シリアル・チャンネル・互換なメディア形式**が一致するブロックをまとめ、累積フレーム位置で並べる。循環世代や物理LBAが変わっても同じ連続録画を保つ。物理カード末尾から先頭へ一周する実例でも、LBA順にして時系列を逆転させない。録画開始D103が上書きされて欠けていても、残存する継続ブロックの検証済み参照を利用する。

これはカードの**録画セッション**の復元であり、車両イグニッション信号を別に読み取ったものではない。実データのヘッダー種別rawは通常領域1、特別領域2／3／5だった。これを物理カメラ番号だと断定せず、画面ではCH/rawとして扱う。種別やメディア形式が異なるもの、開始参照を検証できない孤立フラグメントは、近い時刻だけを根拠に無理に結合しない。

## Windows版を調べた根拠

korakuenのCraft Anything CLIを実際に`--deep`で実行し、Windows PC Browser 1.9.60.0の一覧・境界・読み取り経路を追加で逆コンパイルした。静的解析であり、Windows実行時の速度測定ではない。

- `0x4FFAE0` / `0x50CB40`：D103/D105管理ヘッダー、D104/D106終端を扱う録画列挙経路。
- `0x4F44C0` / `0x4F4580`：それぞれ開始・継続ヘッダーと対応する終端シグネチャを区別。
- `0x48AA10` / `0x48BFB0`：位置を指定し、`ReadFile(..., 0x200, ...)`で512-byteセクターを読む。後者はSetFilePointerの上下位置も検査。
- `0x544970` / `0x56F960`：管理情報／フレームを解釈する経路として呼び出し元と照合。
- Deep出力の証拠ID：
  - `ev_d3903bfff8d73ccd21ba25781ff2fea7d9bac2f8fded828e7d6e6eb0b391016f`
  - `ev_222db43253aa7c1ca2732841e09e46684e14438e0c014fca256c95fbb4473c7c`
  - `ev_f6472ca24a85ed0caaeea9d4c46d2b05f46261af5a0c07e2743178b951b8a904`

Mac版は原版コードの実行やDLL依存ではなく、上の参照を実IMGと突き合わせた独立実装である。旧Mac版独自の「4MiBの窓を次々読み、圧縮映像・音声を含めて全領域を走査し終えるまで一覧を出さない」方式を通常の入口から外した。

## 新しい読み込み順序

1. **高速カタログ**：MBR、管理領域、ブロック先頭／末尾のD101/D102対を読む。検証した直前参照がある1カメラ形式では、保存ブロック単位で後方リンクをたどる。
2. そのリンクで確定できない領域は、D101/D102の**ヘッダーのみ**を前方にたどる。長さ・自己参照・複製を確認し、H.264・PCM本体を飛ばす。得られた一覧は逐次表示する。
3. **録画の選択時**に、その連続録画だけの全フレームヘッダーを照合。映像は表示に必要なGOPを取得し、音声は別タスクで準備する。音声の全準備を再生開始条件にしない。
4. GPS／音声有無／最高速度のフィルターに必要な情報が未確認なら、その行は未確認として残す。「全録画の詳細検索」を明示実行した場合だけ、他の録画のヘッダーも照合する。
5. バックアップのSHA-256全体照合は一覧取得後に別タスクで実行する。完了前は**未照合**と表示し、不一致なら表示を停止する。CLIの通常検証では従来通り先に照合し、`--catalog-only`だけは未照合のカタログ検査を許可する。

一覧のフレーム数は末尾の連番等を使った**索引概数**であり、全フレームの検証済み数ではない。API／CLIでも`indexed_frames_estimate`と`validated_frames`を区別する。永続キャッシュは使っていないため、古いカード内容のキャッシュを現在のカードと誤認する経路はない。

不明な長い隙間や破損領域で無制限に走査を続けず、結果に復旧推奨を付ける。高速カタログが未掲載領域にデータがないことを保証するわけではない。必要なら画面の**復旧走査**またはCLIの`--recovery-scan`で、従来の全領域照合を明示実行できる。部分コピーではmanifestの取得範囲だけを扱う。

## 音声と書き出し

各15秒ブロックのPCMは実例で約15.02秒だった。単純にPCMを連結するとブロックごとに約20msの差が蓄積する。そのため次のブロックを映像タイムラインの位置へ合わせ、重複末尾は切り詰め、不足は8bit unsignedなら128、16bitなら0の無音で補う。異なる音声形式は混在させない。最終末尾の微小な差は表示し、長時間のメーカー実装とのサンプル単位の一致は保証しない。

再生・シーク・範囲書き出し・GPS／センサー・MP4／WAVは連続録画の1本のタイムラインを使う。`.pcbbackup`は結合元の**全ブロックの管理ヘッダーと元パケット**を保持し、補正した音声で原データを書き換えない。旧版のブロック単位しおりは、それを含む連続録画へ引き継ぐ。

## 検証の区別

- 68件の合成単体テストに、ブロック結合、特別領域のD103継続、別セッション／CH／形式の分離、循環世代をまたぐ順序、壊れた／循環する後方リンク、ペイロードを読まない索引、選択範囲限定の読込、未取得範囲、遅延時の破損検知、音声境界の切り詰め／無音、結合バックアップと遅延ハッシュ検査を含む。
- korakuenでは全31,486,640,128 bytesの実IMGに対して独立Pythonプロトタイプを照合し、旧全走査の993保存ブロック・439,666フレームに対する欠落0を確認した。約145.25MiBの要求読み取り、約6〜7秒。ファイルキャッシュの影響を排除したSD実機ベンチマークではない。
- Macの全カード規模の構造検査には、全D101/D102とカタログが参照したセクターだけを抽出した**メタデータ用スパースfixture**を使う。映像・PCM本体を含まないため、全カード映像のMacデコード成功とは区別する。
- Macの映像・音声・GUIの連続再生検査には、別に実ペイロード付き1,200フレームの部分バックアップを使う。

詳細な測定結果と検証範囲は[今回の検証記録](validation-catalog.md)を参照。
